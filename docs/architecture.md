# Архитектура системы «Умный кредитный кабинет предпринимателя»

## 1. Назначение системы

«Умный кредитный кабинет предпринимателя» — веб-приложение для подачи и отслеживания заявок на кредитование малого и микробизнеса.

Система позволяет пользователю ознакомиться с кредитными продуктами, заполнить заявку, отправить её на обработку и получить результат рассмотрения. Обработка заявки включает проверку введённых данных, имитацию внешних проверок, расчёт демонстрационного скорингового балла и формирование предварительного решения.

Проект реализуется в формате MVP для демонстрации полного цикла обработки кредитной заявки. Реальные банковские и государственные интеграции не используются.

## 2. Технологический стек

| Компонент | Технология | Назначение |
|---|---|---|
| Frontend | React, TypeScript, Vite | Пользовательский интерфейс |
| Backend | Python, FastAPI | REST API и бизнес-логика |
| Валидация данных | Pydantic | Проверка входящих запросов и формирование ответов |
| База данных | PostgreSQL | Хранение заявок, продуктов, проверок и решений |
| ORM | SQLAlchemy | Работа с данными через Python-модели |
| Миграции | Alembic | Управление изменениями схемы БД |
| Тестирование backend | pytest | Автоматическая проверка серверной логики |
| Документация API | OpenAPI, Swagger UI | Описание и ручная проверка API |
| Контейнеризация | Docker, Docker Compose | Воспроизводимый запуск компонентов |

## 3. Общая архитектура

Система состоит из трёх основных компонентов:

1. **Frontend** — отображает интерфейс, принимает данные пользователя и отправляет HTTP-запросы.
2. **Backend** — проверяет запросы, выполняет бизнес-логику, организует проверки и принятие демонстрационного решения.
3. **PostgreSQL** — хранит данные кредитных продуктов, заявок, результатов проверок и истории изменений статусов.

Backend взаимодействует с базой данных. Внешние проверки компании и кредитной истории реализуются с помощью имитационных сервисов (mock-сервисов).

## 4. Взаимодействие компонентов

Основной сценарий взаимодействия:

1. Пользователь открывает веб-приложение.
2. Frontend запрашивает у backend список доступных кредитных продуктов.
3. Пользователь выбирает продукт и заполняет форму заявки.
4. Frontend отправляет данные заявки в backend.
5. Backend проверяет корректность входных данных.
6. Backend сохраняет заявку в PostgreSQL.
7. При отправке заявки на рассмотрение backend выполняет имитацию внешних проверок и рассчитывает скоринговый балл.
8. На основании заданных демонстрационных правил формируется результат: одобрение, отказ или альтернативное предложение. При недостатке данных может потребоваться их уточнение.
9. Backend сохраняет результат и обновляет статус заявки.
10. Frontend получает актуальный статус и отображает результат пользователю.

## 5. Структура backend

Backend организуется по функциональным слоям:

- `app/api/` — REST-маршруты и обработчики HTTP-запросов.
- `app/schemas/` — схемы входных и выходных данных на основе Pydantic.
- `app/models/` — ORM-модели сущностей базы данных.
- `app/services/` — бизнес-логика обработки заявок, скоринга и принятия решения.
- `app/repositories/` — операции чтения и записи в базу данных.
- `app/integrations/` — имитация внешних проверок.
- `app/config.py` — настройки приложения и переменные окружения.
- `app/main.py` — создание экземпляра FastAPI и подключение маршрутов.

Такое разделение позволяет независимо развивать API, бизнес-логику и работу с базой данных.

## 6. Основные сущности данных

В системе предусматриваются следующие сущности:

- **Client** — информация о клиенте или предпринимателе.
- **CreditProduct** — доступный кредитный продукт и его параметры.
- **Application** — кредитная заявка, её параметры и текущий статус.
- **Verification** — результаты проверок заявки.
- **CreditDecision** — результат скоринга и принятое демонстрационное решение.
- **ApplicationHistory** — история изменения статусов заявки.

Данные сущности связаны между собой. Клиент может иметь несколько заявок, один кредитный продукт может использоваться в нескольких заявках, а у заявки может быть несколько проверок и записей истории. Для MVP предполагается не более одного итогового решения на одну заявку.

## 7. Обработка заявки и статусы

Предусматриваются следующие статусы:

- `DRAFT` — черновик заявки.
- `SUBMITTED` — заявка отправлена.
- `CHECKING` — выполняются проверки.
- `APPROVED` — заявка одобрена.
- `REJECTED` — отказ.
- `ALTERNATIVE_OFFER` — предложены альтернативные условия.
- `NEEDS_INFO` — требуется уточнение данных.

Изменение статусов выполняется на backend в соответствии с заданными правилами переходов. Frontend не должен самостоятельно назначать произвольный статус.

Для каждой заявки предусматривается хранение истории изменений статусов. Детальные правила переходов описываются в документе `application-states.md`.

## 8. Развёртывание

Для локального запуска используется Docker Compose, объединяющий frontend, backend и PostgreSQL.

Конфигурация приложения задаётся через переменные окружения. В репозитории хранится файл `.env.example` с перечнем необходимых параметров без секретных значений.

Для разработки frontend и backend также могут запускаться локально отдельно. API документируется с помощью Swagger UI, доступного по адресу `/docs` при работающем backend.

## 9. Тестирование

Проверка системы включает:

- тестирование отдельных функций бизнес-логики;
- проверку валидации входных данных;
- проверку REST API;
- проверку сохранения заявок и решений в базе данных;
- проверку переходов между статусами;
- сквозной тест основного сценария от создания заявки до отображения результата.

## 10. Ограничения MVP

- Внешние банковские и государственные сервисы заменены имитационными проверками.
- Скоринговая модель является демонстрационной и не предназначена для реального кредитования.
- Принятое системой решение не является фактическим банковским решением.
- Реальные платёжные операции и передача данных в банковские системы не выполняются.
- Система предназначена для демонстрации технической реализации кредитного процесса.
