# Smart Credit Cabinet — Backend

## 1. Описание проекта

Backend Smart Credit Cabinet — серверная часть веб-приложения для подбора кредитных продуктов для бизнеса и управления кредитными заявками.

Backend отвечает за:
- регистрацию и авторизацию пользователей;
- хранение пользовательских данных и кредитных заявок;
- проверку прав доступа;
- создание, просмотр, редактирование и отправку кредитных заявок;
- получение и сравнение кредитных продуктов;
- расчёт ориентировочных параметров кредита;
- предоставление API для взаимодействия с frontend.

## 2. Технологический стек

| Технология | Назначение |

## 4. Назначение каталогов и файлов

### 4.1. `app/api/` — HTTP-эндпоинты

Слой API принимает HTTP-запросы от frontend, вызывает соответствующие сервисы и возвращает ответы.

**`auth.py` — реализован**

Отвечает за:
- регистрацию пользователя;
- вход по логину и паролю;
- выдачу JWT-токена;
- получение информации о текущем авторизованном пользователе.

**`applications.py` — реализован**

Отвечает за HTTP-операции с кредитными заявками:
- создание заявки;
- получение списка заявок текущего пользователя;
- получение заявки по ID;
- редактирование заявки;
- отправку заявки на рассмотрение.

В этом слое также проверяются права доступа и допустимость операции в соответствии с текущим статусом заявки.

**`products.py` — будущий файл**

Будет содержать эндпоинты каталога кредитных продуктов:
- `GET /api/v1/products` — список доступных продуктов;
- `GET /api/v1/products/{product_id}` — информация об отдельном продукте.

При необходимости позднее можно добавить эндпоинт подбора и сравнения предложений.

### 4.2. `app/core/` — базовая конфигурация

**`config.py` — реализован**

Загружает настройки приложения из переменных окружения:
- название приложения;
- режим запуска;
- префикс API;
- параметры подключения к базе данных;
- настройки JWT;
- список разрешённых CORS-origin.

**`database.py` — реализован**

Содержит:
- SQLAlchemy `engine`;
- общий декларативный класс `Base`;
- фабрику сессий `SessionLocal`;
- зависимость `get_db` для получения и закрытия сессии базы данных.

Обработчики API должны получать сессию через `Depends(get_db)`, а не создавать отдельное подключение в каждом эндпоинте.

**`security.py` — реализован**

Отвечает за функции безопасности:
- хеширование паролей;
- проверку введённого пароля;
- создание JWT-токена;
- декодирование и проверку токена;
- получение текущего пользователя через механизм авторизации.

Секреты и ключи не должны храниться непосредственно в исходном коде.

### 4.3. `app/models/` — модели базы данных

Модели SQLAlchemy описывают таблицы и связи между ними.

**`user.py` — реализован**

Модель пользователя `User` содержит:
- `id` — идентификатор;
- `email` — уникальный адрес электронной почты;
- `hashed_password` — хеш пароля;
- `created_at` — дата создания пользователя;
- связь с кредитными заявками.

Пароли в открытом виде в базе данных не хранятся.

**`credit_application.py` — реализован**

Модель `CreditApplication` содержит:
- `id` — идентификатор заявки;
- `user_id` — владелец заявки;
- `amount` — запрашиваемая сумма;
- `term_months` — срок кредита в месяцах;
- `purpose` — цель кредита;
- `monthly_income` — ежемесячный доход;
- `employment` — сведения о занятости;
- `status` — текущий статус;
- `comment` — дополнительный комментарий;
- `created_at` и `updated_at` — даты создания и изменения.

Каждая заявка связана с конкретным пользователем через внешний ключ `user_id`.

**`credit_product.py` — будущий файл**

Будет описывать кредитные продукты, доступные для сравнения.

Предполагаемые поля:
- `id` — идентификатор продукта;
- `name` — название продукта;
- `bank_name` — название банка;
- `interest_rate` — процентная ставка;
- `min_amount` и `max_amount` — допустимая сумма;
- `min_term_months` и `max_term_months` — допустимый срок;
- `description` — описание и условия;
- `is_active` — доступность продукта.

Окончательный состав полей нужно согласовать с требованиями проекта.

### 4.4. `app/schemas/` — схемы запросов и ответов

Схемы Pydantic определяют, какие данные API принимает и возвращает. Они отделяют внешний контракт API от структуры таблиц базы данных.

**`auth.py` — реализован**

Содержит схемы регистрации, входа, ответа с данными пользователя и ответа с токеном.

**`application.py` — проверить / добавить**

Должен содержать:
- схему создания заявки;
- схему редактирования заявки;
- схему ответа с данными заявки;
- схему списка заявок, если она необходима;
- проверку допустимых значений полей.

Для редактирования желательно использовать отдельную схему, в которой все изменяемые поля необязательны.

**`product.py` — будущий файл**

Будет содержать схемы:
- создания продукта, если добавление продуктов через API потребуется;
- ответа с данными продукта;
- списка продуктов;
- параметров подбора и сравнения кредитов.

Не следует отдавать клиенту внутренние поля, которые ему не нужны.

### 4.5. `app/repositories/` — доступ к данным

Репозитории инкапсулируют операции чтения и записи в базу данных. Их использование помогает не дублировать SQLAlchemy-запросы между сервисами.

**`user.py` — добавить при необходимости**

Будет содержать поиск пользователя по ID и email, а также операции с пользовательскими данными.

**`application.py` — добавить при необходимости**

Будет содержать запросы к кредитным заявкам:
- получение заявок пользователя;
- поиск заявки с учётом владельца;
- сохранение и обновление заявки.

**`product.py` — будущий файл**

Будет отвечать за чтение каталога кредитных продуктов, поиск по ID, фильтрацию и получение активных предложений.

Если проект пока небольшой, репозитории можно вводить постепенно. Не нужно создавать дополнительные слои только ради структуры — у каждого файла должна быть понятная ответственность.

### 4.6. `app/services/` — бизнес-логика

Сервисы реализуют правила работы приложения. Они не должны зависеть от деталей HTTP-ответов и Swagger.

**`auth.py` — реализован**

Содержит логику регистрации и аутентификации пользователя, включая проверку существования email и проверку пароля.

**`applications.py` — будущий файл / возможное выделение логики**

По мере роста проекта в него можно вынести:
- создание заявки;
- проверку владельца;
- проверку возможности редактирования;
- изменение статусов;
- отправку заявки на рассмотрение.

Сейчас часть логики уже находится в `api/applications.py`. Переносить её в сервис следует при реальном усложнении, а не дублировать реализацию.

**`products.py` — будущий файл**

Будет отвечать за бизнес-логику каталога и подбора кредитных продуктов:
- фильтрацию продуктов по сумме;
- проверку допустимого срока;
- применение условий продукта;
- формирование списка подходящих предложений;
- сортировку результатов.

**`credit_calculator.py` — будущий файл**

Будет содержать функции финансовых расчётов:
- расчёт ориентировочного ежемесячного аннуитетного платежа;
- расчёт общей суммы выплат;
- расчёт переплаты.

Расчёты должны учитывать используемую процентную ставку и период начисления процентов. Если комиссии и дополнительные платежи не включены в модель, результат нужно обозначать как предварительную оценку.

### 4.7. `app/utils/` — вспомогательные функции

**`exceptions.py` — необязательный будущий файл**

Может содержать общие пользовательские исключения и вспомогательные функции для единообразной обработки ошибок. Создавать его стоит, если аналогичная логика начинает повторяться.

### 4.8. `app/main.py` — точка входа приложения

Файл уже существует.

Он отвечает за:
- создание экземпляра FastAPI;
- настройку метаданных приложения;
- подключение CORS;
- подключение роутеров авторизации и кредитных заявок;
- формирование общей структуры API.

Новые роутеры необходимо подключать здесь, чтобы их эндпоинты появились в Swagger.

## 5. Работа с базой данных

### 5.1. Миграции Alembic

Каталог `alembic/versions/` содержит версии схемы базы данных.

Миграция `d2eefc340c25` создаёт таблицу `credit_applications`, связанную с таблицей `users`.

После добавления модели или изменения существующей таблицы необходимо создать миграцию и проверить её содержимое.

Создание миграции выполняется из каталога `backend`:

```powershell
.\.venv\Scripts\python.exe -m alembic revision --autogenerate -m "describe changes"
```

Применение миграций:

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade head
```

Проверка текущей ревизии:

```powershell
.\.venv\Scripts\python.exe -m alembic current
```

Не заменяйте миграции ручным созданием таблиц или вызовом `Base.metadata.create_all()` в обычном процессе разработки.

### 5.2. Добавление новой модели

При добавлении новой модели необходимо:
1. Создать файл модели в `app/models/`.
2. Импортировать модель в `app/models/__init__.py`, если проект использует этот файл для регистрации моделей.
3. Проверить, что Alembic импортирует все модели через свой `env.py`.
4. Создать миграцию.
5. Проверить `upgrade()` и `downgrade()`.
6. Применить миграцию к локальной базе.

## 6. API-контракты

Все API-эндпоинты имеют общий префикс `/api/v1`.

### Авторизация

| Метод | Эндпоинт | Назначение |
|---|---|---|
| POST | `/api/v1/auth/register` | Регистрация пользователя |
| POST | `/api/v1/auth/login` | Вход и получение токена |
| GET | `/api/v1/auth/me` | Данные текущего пользователя |

### Кредитные заявки

| Метод | Эндпоинт | Назначение |
|---|---|---|
| POST | `/api/v1/applications` | Создание заявки |
| GET | `/api/v1/applications` | Список своих заявок |
| GET | `/api/v1/applications/{application_id}` | Получение заявки |
| PATCH | `/api/v1/applications/{application_id}` | Редактирование заявки |
| POST | `/api/v1/applications/{application_id}/submit` | Отправка заявки |

### Кредитные продукты — планируются

| Метод | Эндпоинт | Назначение |
|---|---|---|
| GET | `/api/v1/products` | Каталог кредитных продуктов |
| GET | `/api/v1/products/{product_id}` | Подробная информация о продукте |

Подбор и сравнение продуктов будут добавлены после согласования бизнес-логики и схем запросов и ответов.

## 8. Локальный запуск

### Требования

- Python 3.13;
- PostgreSQL 18;
- Git.

### Установка зависимостей

Из корня репозитория:

```powershell
cd backend
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

### Настройка окружения

Создайте `backend/.env` на основе `backend/.env.example` и заполните параметры подключения к PostgreSQL и JWT.

### Применение миграций

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade head
```

### Запуск сервера

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload
```

Документация API:

http://127.0.0.1:8000/docs

Остановка сервера — `Ctrl+C`.

## 9. Конфигурационные файлы

**`.env`**

Локальные настройки и секреты. Не должен попадать в Git.

**`.env.example`**

Безопасный шаблон настроек, который каждый разработчик копирует в `.env`.

**`requirements.txt`**

Список Python-зависимостей, необходимых для запуска приложения.

**`alembic.ini`**

Конфигурация Alembic.

**`alembic/env.py`**

Настройка окружения миграций, включая получение URL подключения и метаданных моделей.

**`.gitignore`**

Должен исключать `.env`, `.venv/`, `__pycache__/`, `*.py[cod]` и другие локальные или временные файлы.

## 10. Правила разработки

1. Используйте отдельные feature-ветки для задач.
2. Согласовывайте изменения API-контрактов с frontend-разработчиком.
3. Не коммитьте секреты и локальные конфигурации.
4. Используйте `Depends(get_db)` для получения сессии базы данных.
5. Не выполняйте SQL-запросы к базе напрямую из frontend.
6. Изменяйте структуру БД через Alembic.
7. Проверяйте миграции перед применением.
8. Добавляйте тесты для новой бизнес-логики.
9. Создавайте Pull Request перед слиянием в основную ветку.
