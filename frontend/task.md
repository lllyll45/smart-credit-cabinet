# Задача: обновить frontend Smart Credit Cabinet под актуальный API

## Цель

Актуализировать пользовательский интерфейс под изменения backend API: обновить форму кредитной заявки, отображение предварительной оценки и статусов, а также добавить интерфейс сотрудника банка (`staff`) для обработки заявок.

## 1. Обновить форму создания кредитной заявки

Форма должна соответствовать актуальной схеме `CreditApplicationCreate`.

Обязательные поля:
- Кредитный продукт (`credit_product_id`) — выбор из каталога активных продуктов.
- Сумма кредита (`amount`).
- Срок кредита в месяцах (`term_months`).
- Цель кредита (`purpose`).
- Ежемесячный доход (`monthly_income`).
- Занятость (`employment`).

Требования:
- Загружать список продуктов через `GET /api/v1/products`.
- Показывать основные условия выбранного продукта: банк, процентную ставку, допустимую сумму и срок.
- Проверять заполнение обязательных полей и корректность введённых значений.
- После отправки формы создавать заявку через `POST /api/v1/applications`.
- Не отправлять заявку автоматически на рассмотрение при её создании: создание формирует черновик со статусом `draft`.

## 2. Обновить процесс отправки заявки

Добавить отдельное действие «Отправить на рассмотрение».

При нажатии вызывать:

`POST /api/v1/applications/{application_id}/submit`

После успешного ответа отображать:
- ежемесячный платёж (`monthly_payment`);
- общую сумму выплат (`total_payment`);
- переплату (`overpayment`);
- предварительный результат (`preliminary_result`);
- текущий статус (`status`).

Предварительный результат:
- `likely_eligible` — предварительно подходит по используемому алгоритму;
- `high_debt_burden` — высокая долговая нагрузка по используемому алгоритму;
- `null` — предварительная оценка отсутствует.

Важно: предварительная оценка не является окончательным решением банка. Не следует автоматически менять статус заявки на одобренную или отклонённую.

## 3. Обновить личный кабинет пользователя

Реализовать или актуализировать список заявок через `GET /api/v1/applications`.

Для каждой заявки отображать:
- выбранный кредитный продукт;
- сумму и срок;
- цель кредита;
- ежемесячный платёж и переплату, если расчёт уже выполнен;
- предварительный результат, если он есть;
- статус заявки;
- комментарий сотрудника, если он есть.

Добавить просмотр отдельной заявки через `GET /api/v1/applications/{application_id}`.

Редактирование через `PATCH /api/v1/applications/{application_id}` доступно только для черновиков (`draft`). Для отправленных заявок интерфейс редактирования должен быть недоступен.

## 4. Добавить интерфейс сотрудника банка (`staff`)

Предусмотреть отдельный экран или раздел для сотрудников банка.

Список заявок загружать через:

`GET /api/v1/applications/staff`

Для каждой заявки показывать:
- идентификатор заявки;
- данные пользователя, доступные через текущий API;
- сумму, срок и цель кредита;
- доход и занятость;
- рассчитанный ежемесячный платёж и общую стоимость;
- предварительный результат;
- текущий статус.

Для заявок со статусом `submitted` добавить действия:

**Одобрить**
- Вызвать `POST /api/v1/applications/{application_id}/approve`.
- После успешного ответа обновить данные заявки и отобразить новый статус `approved`.

**Отклонить**
- Предусмотреть поле для ввода причины отказа.
- Вызвать `POST /api/v1/applications/{application_id}/reject`, передав причину в формате, соответствующем схеме `ApplicationRejection`.
- После успешного ответа обновить заявку и отобразить статус `rejected` и причину отказа.

Для заявок со статусами `approved` и `rejected` повторные действия принятия решения не показывать.

## 5. Учесть роли и авторизацию

- Использовать существующий механизм входа и JWT-токен.
- Передавать токен в заголовке `Authorization: Bearer <token>` при обращении к защищённым эндпоинтам.
- Разделять интерфейс пользователя и сотрудника на основании роли, полученной от backend.
- Не определять роль по адресу электронной почты или другим предположениям на frontend.
- Обрабатывать ответы `401 Unauthorized`, `403 Forbidden`, `404 Not Found`, `409 Conflict` и ошибки валидации `422 Unprocessable Entity`.

Проверка роли на frontend нужна для отображения интерфейса, но не заменяет серверную проверку прав доступа.

## 6. Обработка состояний интерфейса

Для всех запросов предусмотреть:
- состояние загрузки;
- отображение ошибок;
- уведомление об успешном выполнении действия;
- обновление данных после создания, отправки, одобрения или отказа;
- защиту от повторного нажатия кнопок во время выполнения запроса.

## 7. Критерии приёмки

1. Пользователь может выбрать кредитный продукт и заполнить обновлённую форму заявки.
2. Создание заявки формирует черновик `draft`.
3. Пользователь может отдельно отправить черновик на рассмотрение.
4. После отправки отображаются расчёты и предварительный результат, если он возвращён API.
5. Пользователь видит актуальные статусы собственных заявок.
6. Сотрудник с соответствующими правами может просматривать список заявок.
7. Сотрудник может одобрить заявку или отклонить её с указанием причины.
8. После решения статус и комментарий обновляются в интерфейсе.
9. Предварительная оценка не подменяет окончательное решение сотрудника.
10. Интерфейс корректно обрабатывает ошибки API и состояния загрузки.
11. Полный сценарий проверен через браузер: создание заявки → отправка → предварительная оценка → решение сотрудника → отображение результата пользователю.

## Важно

Перед реализацией сверить поля ответа авторизации, формат `ApplicationRejection` и доступные данные пользователя с актуальными Pydantic-схемами backend. Не добавлять на frontend поля, которых API не возвращает.
