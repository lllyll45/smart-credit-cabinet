# Smart Credit Cabinet — Frontend

## 1. О проекте

Frontend — клиентская часть приложения **Smart Credit Cabinet**, предназначенного для подбора кредитных продуктов для бизнеса, сравнения условий и управления заявками на кредит.

Пользователь должен иметь возможность:

- зарегистрироваться и войти в систему;
- просматривать доступные кредитные продукты;
- указывать параметры бизнеса и потребность в финансировании;
- сравнивать кредитные предложения;
- рассчитывать ежемесячный платёж и переплату;
- создавать и редактировать черновики заявок;
- отправлять заявки на рассмотрение;
- просматривать список своих заявок и их статусы.

Frontend взаимодействует с backend через REST API. Бизнес-логика, работа с базой данных, проверка прав доступа и изменение статусов заявок выполняются на backend.

## 4. Назначение основных файлов и папок

### `src/app/` — настройка приложения

**`App.tsx`**

Корневой компонент приложения. Определяет общую структуру отображения и подключает маршрутизацию.

**`router.tsx`**

Содержит маршруты приложения и связывает URL с соответствующими страницами.

Примеры маршрутов:

- `/login` — вход;
- `/register` — регистрация;
- `/dashboard` — главная страница личного кабинета;
- `/products` — каталог кредитных продуктов;
- `/products/:productId` — информация о конкретном продукте;
- `/applications` — список заявок;
- `/applications/new` — создание заявки;
- `/applications/:applicationId` — просмотр заявки.

**`providers.tsx`**

В будущем может содержать общие провайдеры приложения: контекст авторизации, глобальные уведомления и другие общие механизмы.

### `src/components/` — переиспользуемые компоненты

Здесь находятся компоненты, которые используются на разных страницах.

**`components/ui/`**

- `Button.tsx` — единый стиль и поведение кнопок.
- `Input.tsx` — поле ввода.
- `Select.tsx` — выпадающий список.
- `Modal.tsx` — модальное окно.
- `Loader.tsx` — индикатор загрузки.

**`components/layout/`**

- `Header.tsx` — верхняя панель приложения.
- `Sidebar.tsx` — боковое меню.
- `PageLayout.tsx` — общая структура страницы.

Эти компоненты не должны содержать специфичную бизнес-логику отдельных кредитных продуктов или заявок.

### `src/pages/` — страницы приложения

Каждая страница объединяет компоненты и данные для определённого пользовательского сценария.

- `LoginPage.tsx` — форма входа.
- `RegisterPage.tsx` — регистрация пользователя.
- `DashboardPage.tsx` — главная страница с краткой информацией о заявках и предложениях.
- `ProductsPage.tsx` — каталог кредитных продуктов с фильтрами.
- `ProductDetailsPage.tsx` — подробные условия выбранного продукта.
- `ApplicationCreatePage.tsx` — создание новой заявки.
- `ApplicationsPage.tsx` — список заявок пользователя.
- `ApplicationDetailsPage.tsx` — подробности заявки, её статус и доступные действия.
- `NotFoundPage.tsx` — страница для несуществующего маршрута.

Страницы отвечают за композицию интерфейса, а повторно используемая логика выносится в `features/`, `services/` и `hooks/`.

### `src/features/` — функциональные модули

Каждая функциональная область содержит собственные компоненты, типы и работу с API.

#### `features/auth/`

**`authApi.ts`** — запросы регистрации, входа и получения текущего пользователя.

**`authTypes.ts`** — TypeScript-типы пользователя и данных авторизации.

**`AuthContext.tsx`** — общее состояние авторизации и информация о текущем пользователе.

#### `features/products/`

**`productsApi.ts`** — получение списка кредитных продуктов и подробностей о конкретном продукте.

**`productsTypes.ts`** — типы данных кредитных продуктов.

**`ProductCard.tsx`** — карточка кредитного предложения с основными условиями: суммой, сроком, ставкой и другими доступными параметрами.

#### `features/applications/`

**`applicationsApi.ts`** — создание, получение, изменение и отправка заявок.

**`applicationsTypes.ts`** — типы заявок, статусов и данных формы.

**`ApplicationForm.tsx`** — форма с параметрами заявки, например суммой, сроком, целью кредита, ежемесячным доходом и занятостью.

#### `features/calculator/`

**`calculator.ts`** — расчёт ежемесячного платежа, общей суммы выплат и переплаты.

**`CreditCalculator.tsx`** — визуальный компонент калькулятора с полями ввода и результатами расчёта.

Расчёт на frontend нужен для интерактивного предварительного сравнения. При необходимости окончательный расчёт и проверки условий должны выполняться или подтверждаться backend.

### `src/services/` — взаимодействие с backend

**`apiClient.ts`**

Общий HTTP-клиент Axios. В нём настраиваются:

- базовый URL backend;
- заголовки запросов;
- передача токена авторизации;
- единая обработка сетевых ошибок;
- общие настройки HTTP-запросов.

Остальные модули используют общий клиент вместо создания отдельного экземпляра Axios для каждой страницы.

### `src/hooks/` — пользовательские React-хуки

**`useAuth.ts`**

Предоставляет компонентам доступ к информации о текущем пользователе и состоянию авторизации.

Дополнительные хуки можно создавать, когда логика действительно повторяется в нескольких компонентах.

### `src/types/` — общие типы

**`common.ts`**

Содержит общие типы, используемые несколькими функциональными модулями, например структуру ответа API или параметры пагинации.

Типы конкретных продуктов и заявок лучше хранить рядом с соответствующими функциональными модулями.

### `src/utils/` — вспомогательные функции

**`formatCurrency.ts`**

Форматирует денежные значения, например отображает сумму в рублях с разделителями разрядов.

**`formatDate.ts`**

Преобразует даты в удобный для пользователя формат.

В этой папке не следует размещать компоненты React или запросы к API.

### `src/styles/` — общие стили

**`global.css`**

Содержит глобальные CSS-правила, базовую типографику, общие цвета, фон, сброс стандартных отступов и другие настройки интерфейса.

Стили отдельных компонентов предпочтительно хранить рядом с ними или в CSS Modules.

### `src/main.tsx` — точка входа

Запускает React-приложение и подключает корневой компонент `App.tsx`.

### `tests/` — тесты frontend

- `auth.test.tsx` — тесты формы входа и регистрации.
- `products.test.tsx` — тесты каталога и отображения кредитных предложений.
- `calculator.test.ts` — тесты расчётов кредитного калькулятора.

При увеличении проекта тесты можно хранить рядом с соответствующими функциональными модулями.

## 5. Взаимодействие с backend

Backend запускается локально по адресу:

`http://127.0.0.1:8000`

Swagger-документация доступна по адресу:

`http://127.0.0.1:8000/docs`

Frontend обращается к backend через HTTP-запросы. Основные адреса API:

| Метод | Endpoint | Назначение |
|---|---|---|
| `POST` | `/api/v1/auth/register` | Регистрация |
| `POST` | `/api/v1/auth/login` | Вход |
| `GET` | `/api/v1/auth/me` | Информация о текущем пользователе |
| `GET` | `/api/v1/products` | Каталог продуктов — планируется |
| `GET` | `/api/v1/products/{product_id}` | Детали продукта — планируется |
| `POST` | `/api/v1/applications` | Создание заявки |
| `GET` | `/api/v1/applications` | Список заявок пользователя |
| `GET` | `/api/v1/applications/{application_id}` | Получение заявки |
| `PATCH` | `/api/v1/applications/{application_id}` | Изменение заявки |
| `POST` | `/api/v1/applications/{application_id}/submit` | Отправка заявки |

Список продуктов является планируемой частью API. Перед реализацией запросов необходимо сверить фактические endpoint и схемы ответов с backend-разработчиками и Swagger.

## 6. Настройка окружения

В корне `frontend/` создаётся файл `.env`.

Пример содержимого `.env.example`:

```dotenv
VITE_API_BASE_URL=http://127.0.0.1:8000/api/v1
```

Файл `.env.example` хранится в Git и содержит только пример конфигурации. Локальный `.env` используется разработчиком и не должен содержать секреты, которые нельзя раскрывать в клиентском коде.

Переменные Vite с префиксом `VITE_` доступны в браузере. Поэтому пароль базы данных, секрет JWT и другие приватные ключи нельзя размещать во frontend `.env`.

В коде базовый URL можно получать через `import.meta.env.VITE_API_BASE_URL`.

## 8. Авторизация

После входа backend возвращает токен доступа в соответствии с текущим контрактом API.

Frontend должен:

1. Отправить данные формы на endpoint входа.
2. Обработать успешный ответ и ошибки.
3. Передавать токен в запросах, требующих авторизации, в соответствии с контрактом backend.
4. Получать данные пользователя через `/auth/me`.
5. Ограничивать отображение страниц и действий в интерфейсе согласно состоянию авторизации.

Важно: скрытие кнопки или страницы на frontend не заменяет проверку прав доступа на backend. Backend обязан самостоятельно проверять владельца каждой заявки.

Способ хранения токена следует согласовать с backend-разработчиками. Нельзя считать `localStorage` полностью безопасным хранилищем при наличии уязвимостей XSS.

## 9. Работа с заявками

Предполагаемый сценарий работы пользователя:

1. Пользователь входит в систему.
2. Открывает каталог кредитных продуктов.
3. Изучает условия предложений.
4. Выбирает подходящий продукт или переходит к форме подбора.
5. Указывает сумму, срок, цель кредита и необходимые финансовые параметры.
6. Создаёт черновик заявки.
7. Проверяет и при необходимости редактирует данные.
8. Отправляет заявку на рассмотрение.
9. Просматривает статус заявки в личном кабинете.

Frontend отображает статус, полученный от backend, и не должен самостоятельно считать заявку отправленной или одобренной без подтверждения API.

Допустимые переходы между статусами и условия изменения заявки определяются backend.

## 10. Тестирование

Тесты должны проверять не только отображение компонентов, но и поведение пользовательских сценариев.

Примеры проверок:

- отправка пустой формы входа;
- отображение ошибки при неправильных учётных данных;
- загрузка и отображение каталога продуктов;
- отображение состояния загрузки и ошибки сети;
- валидация полей заявки;
- корректный расчёт ежемесячного платежа;
- отображение списка заявок и их статусов;
- обработка ошибки доступа к заявке.

Тесты не должны зависеть от реальной базы данных или работающего production-сервера. Для API-запросов используются моки или тестовые ответы.

## 11. Правила разработки

1. Перед началом работы обновите свою ветку от основной ветки проекта.
2. Для каждой задачи создавайте отдельную feature-ветку.
3. Не изменяйте API-контракт без согласования с backend-разработчиками.
4. Используйте TypeScript-типы для запросов и ответов API.
5. Не дублируйте общий HTTP-клиент в разных модулях.
6. Показывайте пользователю состояния загрузки, ошибки и отсутствия данных.
7. Не храните секреты в клиентском коде.
8. Не размещайте всю логику приложения в одном компоненте.
9. Перед Pull Request проверьте сборку и доступные тесты.
10. Не коммитьте `node_modules/`, `dist/` и локальный `.env`.

Пример создания feature-ветки:

```powershell
git switch main
git pull
git switch -c feature/products-page
```

После реализации задачи создайте коммит и откройте Pull Request в основную ветку.

## 12. Этапы реализации

### Этап 1. Базовая настройка

- Инициализировать React + TypeScript + Vite.
- Настроить маршрутизацию.
- Создать общий HTTP-клиент.
- Подключить стили и общий layout.

### Этап 2. Авторизация

- Создать формы входа и регистрации.
- Подключить API авторизации.
- Реализовать состояние текущего пользователя.
- Обработать ошибки API.

### Этап 3. Заявки

- Создать форму заявки.
- Реализовать создание и редактирование черновика.
- Вывести список заявок.
- Реализовать просмотр заявки и её отправку.

### Этап 4. Кредитные продукты

- Согласовать структуру продукта с backend.
- Реализовать каталог и карточки предложений.
- Добавить подробную страницу продукта.
- Реализовать фильтрацию и сравнение условий после появления соответствующих endpoint.

### Этап 5. Калькулятор и подбор

- Реализовать расчёт платежа и переплаты.
- Добавить предварительный подбор по параметрам бизнеса.
- Согласовать с backend правила расчёта и допустимые условия кредитования.

### Этап 6. Проверка и подготовка демонстрации

- Проверить все основные пользовательские сценарии.
